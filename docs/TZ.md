## 1. Общие сведения

### 1.1. Цель
Современный, быстрый, SEO-ориентированный интернет-магазин мультибрендовой одежды. Объём каталога: 1 500 SKU на старте, до 10 000+ через 2–3 года. Сайт поддерживает сотрудник без навыков программирования; разработчиков в штате на старте нет.

### 1.2. Ключевые принципы
1. **МойСклад — источник правды** по товарам, ценам, остаткам и заказам. Сайт не позволяет продать то, чего нет на складе.
2. **Всё, что видит поисковик, отдаётся готовым HTML с сервера** (SSR/ISR). Никакого контента, который появляется только после выполнения JavaScript.
3. **Сотрудник меняет всё содержимое сам**, без программиста: товары, фото, тексты, баннеры, главную, страницы, SEO-поля, редиректы.
4. **Безопасность и восстановление заложены с первого дня.** Сайт можно поднять на новом сервере из бэкапа за 1–2 часа.
5. **Хостинг и персональные данные — в РФ** (152-ФЗ).
6. **Никаких «временных» решений в SEO-структуре.** Адреса страниц задаются один раз и не меняются.

## 2. Модель каталога

### 2.1. Правила ведения товаров в МоемСкладе (обязательны для сотрудников)
Актуализировано 08.11.2026 по фактическим данным МС (3 075 товаров, 12 519 модификаций). Подробная инструкция для сотрудников — [docs/moysklad.md](moysklad.md).

- **Один товар в МоемСкладе = одна модель одного цвета.** Модификации = только размеры (характеристика «Размер»). Так у каждого цвета своя страница на сайте. *Подтверждено: так ведётся каталог сейчас.*
- **Название:** «Тип Бренд Модель Цвет». Бренд и цвет сайт определяет из названия, если доп. поля не заполнены.
- **Доп. поля МС** (существующие): «Бренд», «Для кого», «Цвет», «Длина», «Ширина», «Высота», «Ссылка на товар» (адрес на старом сайте — источник редиректов, п. 7.14). Заполнять желательно; если заполнены — важнее автоопределения.
- **Пол по умолчанию — «Мужское»** (≈90% ассортимента). Женское и унисекс — по полю «Для кого» или слову в названии; остальное правится вручную.
- **Типы цен:** «Цена продажи» — цена на сайте, «Старая цена» — зачёркнутая (только если больше цены продажи). Цены берутся с модификации, если там пусто — с товара.
- **Склад интернет-магазина:** «Основной склад (Партизанская 5а/8)». Остальные склады на сайт не влияют.
- **Вес и габариты** сейчас не заполнены ни у одного товара: для доставки используются значения по умолчанию для категории (п. 5.2), заполнять постепенно.
- **Размеры** нормализуются автоматически: «One size» → «One Size», русская «М» → «M», «32х32» → «32x32», «42 EUR» / «42 EU» → «42 EU», «42,5» → «42.5». Поле «Артикул» не используется; SKU = код модификации МС, штрихкод — EAN-13 модификации.
- **«(B)» в конце названия — товар с браком.** Пометка остаётся в названии на сайте (решение от 08.11.2026).
- Цвета одной модели связываются по общей части названия [Потом]: поле «Артикул модели» пока не вводится.

### 2.2. Сущности на сайте

| Сущность | Где хранится | Примечание |

## 3. Интеграция с МоимСкладом

### 3.1. Технические условия
- JSON API 1.2, отдельный технический пользователь МС с минимально нужными правами, токен хранится только в переменных окружения.
- Соблюдение лимитов API: не более 45 запросов за 3 секунды и не более 5 параллельных. Очередь запросов с ограничением скорости и повтором при ответе 429.
- Каждая операция синхронизации логируется: что, когда, результат, ошибка.

### 3.2. Товары и модификации (МС → сайт) [MVP]
- **Первичный импорт**: все товары из выбранных групп, постранично, можно перезапускать (идемпотентно, сопоставление по `id` МС).
- **Инкрементальные обновления**: вебхуки МС на `product` и `variant` (CREATE / UPDATE / DELETE).
- **Страховочная сверка** раз в 30 минут: товары, изменённые с момента последней сверки (`updated`).
- Удаление или архивирование в МС → товар снимается с публикации; страница отвечает по правилам п. 7.6.
- Группы товаров МС сопоставляются с категориями сайта через таблицу соответствия в админке: структура МС не обязана совпадать со структурой сайта.
- **Создаются только товары с ценой и свободным остатком > 0** (решение от 08.11.2026). Товар, уже созданный на сайте, обновляется всегда и при нулевом остатке остаётся с пометкой «Нет в наличии» (п. 7.6).
- **Бренд:** поле «Бренд» → иначе поиск по названию в справочнике брендов (модуль `brand`, с вариантами написания). Новые значения поля «Бренд» добавляются в справочник автоматически.
- **Цвет:** поле «Цвет» → иначе последнее цветовое слово названия (словарь английских названий цветов). Бренд вырезается из названия перед поиском цвета.
- **Категории:** группы МС сопоставляются с категориями сайта (metadata `moysklad_folder_id`), новые группы создают категории автоматически. Группа «Товары интернет-магазинов» игнорируется.
- **Фото** при создании товара забираются из МС (до 12 шт., в исходном порядке) и загружаются в хранилище сайта. Дальше фото принадлежат сайту.
- **Зачёркнутая цена** хранится в `metadata.compare_at_price` варианта.
- Изменения определяются по хешу полей: неизменённые товары не перезаписываются.

### 3.3. Остатки (МС → сайт) [MVP]
- Учитываются только склады из настройки «склады для интернет-магазина».
- Доступно к продаже = остаток − резерв.
- Обновление: вебхук изменения остатков (`webhookstock`) + сверка всех остатков раз в 10 минут.
- При оформлении заказа остаток проверяется ещё раз на стороне сервера.

### 3.4. Заказы (сайт → МС) [MVP]
- После создания заказа на сайте в МС создаётся «Заказ покупателя»: позиции (модификации), цены со скидками, доставка отдельной позицией-услугой, контрагент, канал продаж «Интернет-магазин», комментарий, способ доставки и оплаты, адрес / ПВЗ.
- Контрагент ищется по телефону, затем по email; если не найден — создаётся.
- После оплаты — отметка об оплате (входящий платёж привязывается к заказу).
- Если МС недоступен, заказ сохраняется на сайте и уходит в очередь повторной отправки. Заказ никогда не теряется.

### 3.5. Статусы (МС ↔ сайт) [MVP]
- Таблица соответствия статусов в настройках: Новый → Подтверждён → Собран → Отгружен → Доставлен / Отменён / Возврат.
- Изменение статуса в МС (вебхук `customerorder UPDATE`) обновляет статус на сайте и запускает письмо клиенту.

### 3.6. Панель синхронизации в админке Medusa [MVP]
Последний запуск, ошибки, кнопки «Синхронизировать сейчас» и «Переотправить заказ», список товаров с проблемами (нет бренда, нет категории, нет веса, нет фото).

### 3.7. Маркировка «Честный знак» [Потом]
Сейчас не используется. В позициях заказа предусмотрено поле для кода маркировки, чтобы позже передавать коды в чек без переделки структуры данных.

> Важно: продажа маркируемой одежды без передачи кодов в чек нарушает требования законодательства и грозит штрафами. Рекомендуется вернуться к вопросу до масштабирования.

## 4. Оплата

### 4.1. Т-Касса [MVP]
- Модуль `@gorgo/medusa-payment-tkassa`. Одностадийная оплата: карты, СБП, T-Pay.
- **Чеки 54-ФЗ** формируются через Т-Кассу: позиции, доставка, ставка НДС, система налогообложения, ФФД 1.2. Параметры налогообложения задаются в настройках, не в коде.
- Уведомления от Т-Кассы проверяются по подписи (Token). Сумма и номер заказа сверяются с базой. Цене от браузера не доверяем никогда.
- Возвраты (полные и частичные) — из админки, с чеком возврата.
- Тестовый терминал на staging, боевой — только на production.

### 4.2. Яндекс Сплит [Этап 2]
- Свой платёжный провайдер Medusa через API Яндекс Пэй (оплата частями).
- Виджеты Сплита: на карточке товара («4 платежа по N ₽»), в корзине и на странице оформления. Скрипт виджета подгружается отложенно и не влияет на скорость страницы.
- Подпись уведомлений проверяется, возвраты — из админки.

### 4.3. Общие требования
- Неоплаченный заказ держит резерв N минут (настройка, по умолчанию 30). Затем резерв снимается, заказ отменяется.
- Страницы «Оплата прошла» и «Оплата не прошла» с повтором оплаты.
- [Потом] оплата при получении (наложенный платёж) — в зависимости от службы доставки.

## 5. Доставка

### 5.1. Службы
- [MVP] СДЭК: ПВЗ и курьер.
- [MVP] Самовывоз из магазина (если есть офлайн-точка).
- [Этап 2] Почта России, Яндекс Доставка.
- Подключение через ApiShip, одним модулем для всех служб. Если позже откажемся от ApiShip, служба доставки подключается отдельным провайдером, а витрина не меняется: она работает с абстракцией «способ доставки».

### 5.2. Функционал [MVP]
- Определение города: по IP, с подтверждением; ручной выбор с подсказками.
- Расчёт стоимости и сроков в реальном времени по весу и габаритам корзины.
- Выбор ПВЗ на карте (Яндекс Карты) и списком.
- Бесплатная доставка от суммы X (настройка в админке).
- Создание отправления в службе доставки из админки, трек-номер в письме клиенту и в личном кабинете.
- Если товар без веса, используются значения по умолчанию для категории, а товар попадает в отчёт «нет веса».

### 6.2. Каталог [MVP]
- Фильтры: бренд, категория, размер, цвет, цена, пол, сезон, «есть скидка». Значения с количеством товаров; пустые значения скрываются.
- Сортировка: популярные (по умолчанию), новые, дешевле, дороже, скидка.
- Пагинация реальными ссылками (`?page=2`) + кнопка «Показать ещё», которая подгружает следующую страницу и меняет адрес.
- Плитка: фото 3:4, второе фото при наведении (на десктопе), бренд, название, цена, старая цена, метки, доступные размеры.
- Товары без остатка в каталоге не показываются (настройка). Прямая ссылка на товар продолжает работать (п. 7.6).

### 6.3. Карточка товара [MVP]
- Галерея (до 12 фото, зум, свайп на мобильных), бренд (ссылка), название, цена, старая цена, размеры (недоступные зачёркнуты), «Последний размер».
- Другие цвета этой модели (миниатюры-ссылки на соседние страницы).
- Размерная сетка (модальное окно), описание, состав, уход, страна, артикул.
- Блоки: доставка и сроки в город покупателя, способы оплаты, виджет Сплита [Этап 2].
- «Сообщить о поступлении» для отсутствующего размера [Этап 2].
- Рекомендации: «Ещё от бренда», «Похожие», «Вы смотрели».
- Хлебные крошки: Главная → Мужское → Куртки → Stone Island → Товар.

### 6.4. Корзина и оформление [MVP]
- Корзина хранится на сервере (cart id в cookie) и не теряется между сессиями.
- Оформление на одной странице: контакты → доставка → оплата → подтверждение. Без обязательной регистрации.
- Промокоды (скидка %, фиксированная, на бренд или категорию; правила Medusa).
- Чекбокс согласия на обработку ПД — отдельный, не отмеченный по умолчанию; ссылка на политику и оферту.
- Защита от ботов: Яндекс SmartCaptcha (невидимый режим) при подозрительной активности.

### 6.5. Аккаунт [MVP]
- Вход по номеру телефона с SMS-кодом или по email с кодом. Без паролей.
- История заказов со статусами и трек-номерами, адреса, избранное (синхронизируется с локальным после входа).

### 6.6. Уведомления [MVP]
- Клиенту (email, позже SMS): заказ оформлен, оплачен, передан в доставку (с треком), доставлен, отменён.
- Магазину: новый заказ — в Telegram и на email.

### 6.7. Программа лояльности LAFLAMME [MVP]

#### Уровни (утверждённая схема, сентябрь 2026)
| Уровень | Сумма покупок | Скидка |
|---|---|---|
| BASE | до 50 000 ₽ | 0% |
| MEMBER | от 50 000 ₽ | 5% |
| SELECT | от 100 000 ₽ | 10% |
| ICON | от 200 000 ₽ | 15% |
| PRIVATE | от 400 000 ₽ | 15% + VIP-привилегии |

Пороги, проценты и названия уровней хранятся в настройках, а не в коде.

#### Правила начисления (утверждены 08.11.2026)
1. **Сумма покупок** = фактически оплаченная сумма после всех скидок, без стоимости доставки, за вычетом возвратов. Онлайн и офлайн суммируются.
2. **Онлайн-покупка засчитывается через 7 дней после получения заказа клиентом** (статус «Доставлен»), если за это время не оформлен возврат. Возврат после зачёта тоже уменьшает сумму. **Офлайн-покупка** засчитывается сразу по чеку (задержка настраивается отдельно, по умолчанию 0 дней).
3. **Возврат** уменьшает сумму. Если сумма опустилась ниже порога, уровень понижается.
4. **Новый уровень** действует со следующей покупки.
5. **Период накопления — скользящие 12 месяцев:** учитываются покупки, засчитанные за последние 12 месяцев (365 дней). Покупки старше выбывают из суммы, уровень может понизиться. Длина периода и задержка зачёта — в настройках.
6. **Пересчёт уровней** — ежедневно ночью для всех клиентов, а также сразу после зачёта покупки или возврата.
7. **Предупреждение о понижении:** если в ближайшие 30 дней выбывающие покупки опустят клиента на уровень ниже, ему отправляется письмо «Сохраните уровень SELECT: купите на N ₽ до {дата}». В личном кабинете — та же информация.

#### Совмещение скидок
- Товар со скидкой (есть «цена до скидки»): применяется **большая** из двух скидок, они не суммируются.
- Промокоды со скидкой лояльности не суммируются: применяется выгоднейшая для клиента. Исключения задаются в настройках промокода.
- Список исключений (бренды, коллекции, отдельные товары), на которые скидка лояльности не действует, ведётся в админке.
- Скидка рассчитывается только на сервере и отражается в чеке построчно.

#### Источник данных и идентификация
- **Клиент = номер телефона.** Один телефон — один контрагент в МС — один аккаунт на сайте.
- **Расчёт ведёт свой модуль `loyalty` в Medusa.** Встроенная «Накопительная скидка» МС не используется: она не поддерживает скользящий период и задержку зачёта.
- **Журнал операций лояльности** (основа расчёта): каждая запись — клиент, источник (`online` / `offline`), документ (заказ сайта, отгрузка / розничная продажа / возврат МС), сумма, дата покупки, дата зачёта, статус (`pending` → `credited` / `cancelled`). Сумма за 12 месяцев и уровень вычисляются из журнала, поэтому любой расчёт можно проверить и пересчитать.
- **Онлайн-покупки** попадают в журнал из заказов сайта: `pending` при доставке, `credited` через 7 дней.
- **Офлайн-покупки и возвраты** импортируются из МС (розничные продажи, отгрузки, возвраты покупателей) по вебхукам + сверка раз в час. Привязка к клиенту — по контрагенту и телефону. Продажи без контрагента в программе не участвуют.
- **Уровень передаётся обратно в МС**: доп. поле контрагента «Уровень LAFLAMME» и персональная скидка контрагента в процентах (способ уточняется на этапе 2 по возможностям API МС). Касса офлайн-магазина применяет скидку автоматически или кассир видит уровень в карточке клиента.
- **Стартовый расчёт при запуске:** исторические продажи из МС (розничные продажи, отгрузки, возвраты) за последние 12 месяцев загружаются в журнал. Клиенты сразу получают уровни. Данных старого сайта нет, поэтому учитывается только то, что есть в МС.
- Дубли контрагентов (один телефон — несколько карточек) выявляются отчётом и объединяются вручную.
- Ручная корректировка уровня или суммы сотрудником — с указанием причины и записью в журнал.

#### На сайте
- **Корзина и оформление:** скидка применяется автоматически, строка «Скидка LAFLAMME MEMBER −5%».
- **Каталог и карточка:** для вошедшего клиента — «Ваша цена». Подставляется в браузере после загрузки. Серверный HTML, микроразметка и YML-фид всегда содержат обычную цену (SEO и кэш не зависят от пользователя).
- **Личный кабинет:** текущий уровень, накопленная сумма, прогресс до следующего уровня, история начислений (онлайн и офлайн), описание привилегий.
- **Гостю** — блок «Войдите, чтобы получить персональную скидку» и описание программы на странице `/loyalty`.
- **Письма:** о переходе на новый уровень и о понижении.

#### PRIVATE (VIP) [Этап 2]
Набор привилегий — в п. 13. Под них в архитектуре заложены:
- группа клиентов `private` с доступом к закрытым страницам и подборкам (ранний доступ к поступлениям, закрытые распродажи);
- бесплатная доставка по правилу «группа клиентов»;
- отметка VIP в заказе для менеджера и в Telegram-уведомлении.

#### Юридическое

## 7. SEO

### 7.1. Рендеринг и индексируемость [MVP]
- Все индексируемые страницы рендерятся на сервере. В исходном HTML (Ctrl+U) есть H1, текст, цены, ссылки на товары, хлебные крошки, микроразметка.
- Каталог и товары: ISR/кэш с инвалидацией по событию. Изменение товара в Medusa обновляет его страницу и связанные листинги за ≤ 1 минуту.
- Все переходы — настоящие `<a href>`. Фильтры-посадочные — тоже ссылки, а не кнопки.
- Ответ сервера: TTFB ≤ 600 мс для 95% запросов.

### 7.2. Правила адресов (URL) [MVP]
- Только латиница в нижнем регистре, цифры, дефис. Транслитерация по ГОСТ 7.79-2000 (схема Б), упрощённая.
- **Без слеша на конце.** `/men/jackets/` → 301 на `/men/jackets`.
- Главное зеркало: `https://domain.ru`. `http://`, `www.`, адреса в верхнем регистре, двойные слеши, `index.html` → 301 на главное зеркало одним прыжком, без цепочек.
- **Slug категорий и брендов уникальны в общем пространстве имён.** Система не даст создать бренд и категорию с одинаковым slug. Поэтому `/men/{сегмент}` однозначно является категорией, а `/men/jackets/{сегмент}` — брендом.
- Глубина листинга не больше трёх сегментов: `/{пол}/{категория}/{бренд}`. Подкатегории — тоже категории с собственным уникальным slug (`/men/down-jackets`), без вложенности в адресе. Иерархия отражается в хлебных крошках и меню.
- Товар: `/product/{slug}`, где slug = транслит(бренд + название + артикул + цвет). Адрес товара не зависит от категории, поэтому дублей нет.
- **Slug не меняется автоматически** при смене названия. Если сотрудник меняет slug вручную, старый адрес автоматически попадает в редиректы (301).

### 7.3. Фильтры и посадочные страницы [MVP]
**Индексируемые комбинации** — отдельные страницы с чистым адресом:
- пол; пол + категория; пол + категория + бренд;
- бренд; бренд + пол;
- `new` / `sale` + пол.

Посадочная страница создаётся (и попадает в sitemap), только если в ней **≥ 3 товаров в наличии** (порог настраивается). Если товаров стало меньше, страница остаётся доступной с кодом 200, но получает `noindex, follow` и исчезает из sitemap.

**Неиндексируемые параметры** — размер, цвет, цена, сезон, сортировка, `view`:
- адрес вида `/men/jackets?size=m&color=black&sort=price_asc`;
- `<meta name="robots" content="noindex, follow">`;
- `canonical` на страницу без этих параметров;
- параметры всегда в одном порядке (алфавитном), чтобы не плодить варианты.

[Этап 2] Ручные посадочные: сотрудник в админке создаёт страницу вида «Пуховики The North Face» с фиксированным набором фильтров, своим адресом, H1 и текстом.

### 7.4. Пагинация [MVP]
- `?page=N`, у каждой страницы canonical на саму себя. Индексируется.
- `?page=1` → 301 на адрес без параметра.
- На страницах 2+ в title добавляется « — страница N», SEO-текст под листингом не выводится.
- Страница за пределами диапазона → 404.

### 7.5. Мета-теги и заголовки [MVP]
Для каждого типа страниц — шаблон с подстановками. Любое поле можно переопределить вручную в админке.

| Тип | Title | H1 |
|---|---|---|
| Категория | `{Категория} {для мужчин/для женщин} — купить в интернет-магазине {Магазин}` | `{Категория} мужские` |
| Категория + бренд | `{Категория} {Бренд} {мужские} — купить оригинал в {Магазин}` | `{Категория} {Бренд}` |
| Бренд | `{Бренд} — одежда и обувь, купить в {Магазин}` | `{Бренд}` |
| Товар | `{Бренд} {Название} {цвет} — купить за {цена} ₽ в {Магазин}` | `{Бренд} {Название}` |

- Description по шаблону с ценой «от N ₽», количеством моделей, доставкой.
- Одна H1 на странице. Title ≤ 70 символов, description ≤ 160 (обрезка по слову).
- Open Graph и Twitter Card на всех страницах; для товара `og:image` — первое фото.
- Технические страницы (корзина, оформление, аккаунт, поиск, избранное, страницы оплаты): `noindex, nofollow`.

### 7.6. Жизненный цикл товара [MVP]
| Состояние | Ответ сервера | Что видит пользователь | Индексация |
|---|---|---|---|
| В наличии | 200 | обычная карточка | да, в sitemap |
| Временно нет в наличии | 200 | «Нет в наличии», подписка на поступление, похожие товары | да, `availability: OutOfStock`, остаётся в sitemap |
| Снят навсегда (архив в МС) | 301 | на страницу «пол + категория + бренд»; если её нет — на категорию | нет |
| Не существовал | 404 | страница 404 с поиском и популярными категориями | нет |

Отдельные страницы для размеров не создаются.

### 7.7. Микроразметка (JSON-LD) [MVP]
- **Всё сайт:** `Organization` (название, логотип, контакты, соцсети), `WebSite` + `SearchAction`.
- **Хлебные крошки:** `BreadcrumbList` на всех страницах, кроме главной.
- **Товар:** `Product` (name, brand, sku, mpn, color, material, image[], description) + `AggregateOffer` / `Offer` по размерам (price, priceCurrency `RUB`, availability, url, itemCondition `NewCondition`, seller).
- **Листинги:** `ItemList` с товарами текущей страницы.
- **Контакты / магазины:** `ClothingStore` (адрес, часы работы, телефон, геокоординаты).
- **Блог:** `BlogPosting` на странице статьи.
- Разметка проверяется валидатором Яндекса и Schema.org на каждом релизе (автотест на наличие и корректность JSON).

### 7.8. Sitemap и robots.txt [MVP]
- `sitemap.xml` — индекс, ссылающийся на `sitemap-products-{N}.xml` (до 10 000 адресов в файле), `sitemap-categories.xml`, `sitemap-landings.xml`, `sitemap-brands.xml`, `sitemap-pages.xml`, `sitemap-journal.xml`.
- В sitemap только канонические адреса с кодом 200 и `index`. `lastmod` — реальная дата изменения.
- Генерация по расписанию раз в час и по событию, отдача из кэша.
- `robots.txt`:
  - `Disallow: /cart`, `/checkout`, `/account`, `/search`, `/favorites`, `/api/`;
  - для Яндекса: `Clean-param: utm_source&utm_medium&utm_campaign&utm_content&utm_term&yclid&gclid&from&sort&view`;
  - ссылка на sitemap.
- Staging и все тестовые окружения закрыты: basic auth + `X-Robots-Tag: noindex` + `Disallow: /`.

### 7.9. Ответы сервера и редиректы [MVP]
- Настоящие коды 404 и 410 (никаких «мягких 404» с кодом 200).
- **Менеджер редиректов в админке:** старый адрес → новый адрес, тип 301 / 302, массовая загрузка из CSV, счётчик срабатываний.
- Редиректы выполняются на уровне middleware до рендеринга, одним прыжком.
- Автоматические редиректы при смене slug товара, категории или бренда.

### 7.10. Скорость (Core Web Vitals) [MVP]
Целевые значения для мобильных (75-й перцентиль реальных пользователей):
- LCP ≤ 2,5 с; INP ≤ 200 мс; CLS ≤ 0,1.
- Lighthouse Mobile ≥ 90 по Performance, SEO, Best Practices, Accessibility на главной, категории и товаре. Проверка в CI на каждом релизе (Lighthouse CI), с бюджетом.

Как достигается:
- изображения AVIF/WebP, адаптивные размеры (`srcset`), заданные пропорции (нет скачков), `lazy` для всего, кроме первого экрана; первое фото товара и баннер главной — `priority`;
- шрифты на своём сервере, не больше 2 начертаний, `font-display: swap`, preload основного;
- JavaScript на странице товара ≤ 170 КБ (gzip) на первом экране; сторонние скрипты (Метрика, Сплит, карты) — отложенно, после взаимодействия или простоя;
- CDN для статики и фото, долгий кэш с версиями файлов;
- карты подгружаются только при открытии выбора ПВЗ.

## 8. Безопасность

Прошлый сайт был потерян из-за взлома хостинга. Поэтому требования ниже обязательны и проверяются перед запуском.

### 8.1. Сервер и инфраструктура [MVP]
- Сервер в РФ у крупного провайдера. Минимальная ОС (Ubuntu LTS), автоматические обновления безопасности.
- Наружу открыты только порты 80, 443 и SSH (на нестандартном порту). SSH только по ключу, вход root и пароли запрещены, fail2ban.
- PostgreSQL, Redis, Meilisearch **не доступны из интернета**: только во внутренней сети Docker.
- Все сервисы в Docker-контейнерах, работают не от root.
- **Инфраструктура описана кодом** (Docker Compose + скрипты в `infra/`). Новый сервер поднимается одной командой.

### 8.2. Админки [MVP]
- Админка Medusa и Payload — на отдельном поддомене `admin.domain.ru`.
- Доступ ограничен: allowlist IP или вход через VPN / прокси с дополнительной авторизацией. Плюс собственный логин админки.
- Отдельная учётная запись для каждого сотрудника, никаких общих паролей. Минимальные права.
- Пароли от 14 символов, ограничение попыток входа.
- Журнал действий в админке: кто и что изменил.

### 8.3. Приложение [MVP]
- HTTPS везде, HSTS, заголовки безопасности: CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors`.
- Ограничение частоты запросов (rate limit): вход и коды (SMS/email), оформление заказа, промокоды, поиск, формы.
- SmartCaptcha на формах и при подозрительной активности.
- Цены, скидки, стоимость доставки и итог **всегда пересчитываются на сервере**.
- Вебхуки платёжных систем проверяются по подписи. Вебхуки МС принимаются по секретному адресу, со сверкой данных через API МС (не доверяем телу запроса).
- Загрузка файлов в админке: только изображения, проверка типа и размера.
- Секреты только в переменных окружения и менеджере секретов, никогда в git. Разные ключи для staging и production.
- Ошибки не раскрывают внутренности (stack trace только в логах).

### 8.4. Зависимости [MVP]
- Lockfile в репозитории, точные версии.
- Renovate / Dependabot: еженедельные обновления, обновления безопасности — сразу.
- `npm audit` в CI: критические уязвимости блокируют релиз.

### 8.5. Резервное копирование [MVP]
- Базы данных: полный дамп ежедневно + непрерывный журнал (PITR) или дамп каждые 6 часов.
- Фото: версионирование в S3.
- **Бэкапы хранятся у другого провайдера**, не там, где сервер. Хранение 30 дней, шифрование.
- **Раз в месяц — тестовое восстановление** на отдельном сервере, с отметкой в журнале.

### 8.6. Мониторинг [MVP]
- Проверка доступности сайта и ключевых сценариев (главная, товар, добавление в корзину) каждую минуту. Оповещение в Telegram.
- Отслеживание ошибок (Sentry-совместимое, self-hosted или облако с хранением в РФ).
- Алерты: ошибки синхронизации с МС, ошибки платежей, заполнение диска, истечение SSL, бэкап не выполнен.

### 8.7. Юридическое (152-ФЗ, защита прав потребителей) [MVP]
- Персональные данные хранятся и обрабатываются в РФ.
- Уведомление Роскомнадзора об обработке ПД (до запуска).
- Политика обработки ПД; отдельное согласие на обработку ПД (не в тексте оферты); согласие на рассылки — отдельно.
- Баннер cookie: аналитика включается только после согласия.
- Публичная оферта, условия возврата (в том числе дистанционная торговля: 7 дней), реквизиты продавца в подвале.

- Mobile-first: макеты сначала для 375 px. Поддержка последних двух версий Chrome, Safari (iOS), Яндекс Браузера, Firefox, Edge.

- Язык и валюта: русский, RUB; архитектура не мешает добавить второй язык позже.
- Часовой пояс системы: Europe/Moscow.

## 11. Окружения и процесс разработки
- Окружения: `local` (Docker Compose), `staging` (закрыт, тестовые ключи), `production`.
- Git: `main` = production, работа в ветках, слияние через Pull Request.
- CI на каждый PR: линтер, проверка типов, тесты, сборка, Lighthouse CI, `npm audit`.
- Деплой: GitHub Actions → сборка Docker-образов → выкладка на сервер без простоя. Миграции базы данных — автоматически, с бэкапом перед миграцией.
- Тесты: юнит-тесты логики синхронизации, цен и SEO-шаблонов; e2e (Playwright) для сценария «каталог → товар → корзина → оформление → оплата в тестовом режиме».
